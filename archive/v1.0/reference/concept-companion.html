Module 1: Pipelines, DataOps & Experiment Tracking

HOS 1Outcome CO1

Why before you start: Every later HOS assumes you can answer "which data, which code and which settings made the thing that's running?" A pipeline that can't answer that can't be tested, deployed safely, monitored or rolled back.

Three kinds of pipeline

A software pipeline versions and tests code. An MLOps pipeline also versions data and models, because the same code trained on different data is a different model. An AgentOps pipeline also versions prompts, tools and the agent's behaviour, because the same model with a different instruction acts differently.

Why it matters: CO1 asks you to tell these apart, and HOS 1 builds the first two layers for Salish Fresh's model and the third for its agent.

Data versioning (DVC)

Git can't hold large or frequently changing data well, so DVC stores the file in a separate remote and commits a small .dvc file holding its hash. git checkout brings back the hash; dvc checkout brings back the matching file.

Why it matters: A model is only reproducible if you can get back the exact data it was trained on.

A pipeline as stages

dvc.yaml lists stages (validate → train → evaluate), each with its command, dependencies and outputs. dvc repro reruns only the stages whose dependencies changed, by comparing hashes.

Why it matters: "Stage didn't change, skipping" is DVC working, not a bug.

Schema validation (pandera)

A schema states what a batch must look like: columns, types, ranges and rules between values. Validation runs before training, so a bad batch is rejected with a message instead of becoming a quietly worse model.

Why it matters: A renamed column rarely crashes anything. It trains a model that's wrong.

Experiment tracking (MLflow)

Each training run logs its parameters, metrics, the data version and the model file. Each agent evaluation run logs the prompt version, model name and score. The runs table is how you find which change made things worse.

Why it matters: Without the data version and parameters, "it got worse" can't become "batch d3 made it worse".

The model registry

A registered model has numbered versions. An alias such as champion points at the one in production. Promoting or rolling back moves the alias; no run is retrained or changed.

Why it matters: Newest is not the same as production. HOS 2's deploy reads the alias.

Agents vary run to run

Ask the same agent the same ten questions three times and the score moves. One evaluation run can't tell a real improvement from noise.

Why it matters: The spread you measure here sets the gate's margin in HOS 2.
Vocabulary check
Remote
where DVC keeps the actual data files, outside Git.
Stage
one step of a DVC pipeline, with its inputs and outputs.
Run
one recorded training or evaluation in MLflow.
Alias
a movable name, like champion, for one registered model version.
Reproducible
rerunning with the same data, code, settings and seed gives the same result.
Quick self-check before you continue
  • You check out an old commit. Why is the CSV still the new one?
  • Name three things besides the code that can change a model's MAE.
  • Your agent scored 0.82, then 0.76 with no change. What does that mean for judging a prompt edit?
Check your thinking
  1. Git restored the .dvc file's hash, not the data. dvc checkout copies the matching file back from the cache or remote.
  2. The data version, the parameters (including an unpinned random seed), and package versions. Any of them, unpinned, makes a rerun differ.
  3. Run-to-run spread is about 0.06, so a prompt edit needs several runs, and a gain bigger than that spread, before you can call it better.

2️⃣

Module 2: CI/CD/CT for Models & Agents

HOS 2Outcome CO2

Why before you start: HOS 1 made every change traceable. HOS 2 makes every change go through the same checks automatically, so a broken commit, a slower model or a worse prompt is stopped by the pipeline instead of found by users.

CI, CD and the third C

Continuous integration runs fast checks on every push. Continuous delivery/deployment releases what passes. Continuous training retrains on new data, on a schedule or when drift is detected, and sends the result through the same checks.

Why it matters: Models get worse without any code change, because the world changes. CT is the answer to that.

A workflow

A YAML file in .github/workflows/: triggers (on: push, pull_request, schedule, workflow_dispatch), jobs that run on a fresh machine, and steps that run commands.

Why it matters: Scheduled workflows run only on the default branch; workflow_dispatch lets you start one by hand to test it.

Cheap checks first

Unit tests, the data schema and a one-minute training smoke test run on every push. The full evaluation, which costs minutes and model calls, runs before a deploy.

Why it matters: A bug should stop at CI in a minute, before any training or deployment.

The quality gate

A script that compares a candidate with what's deployed and exits non-zero if it isn't better by a margin, on every number it checks. If a number isn't in the gate, the gate can't see it.

Why it matters: A model with better MAE and three times the latency passes an accuracy-only gate.

Gates for agents

An agent never retrains, so its gate runs an evaluation set on every prompt, tool or model change: success rate, and cost per task (tool calls or tokens). The margin comes from the run-to-run spread you measured in HOS 1.

Why it matters: This is how a one-line prompt edit is caught before it reaches customers.

Secrets and rollback

Keys live in repository secrets, never in a workflow file. GitHub masks the exact secret in logs, but not a transformed copy, so a log scan is still worth having. A rollback moves the registry alias back and redeploys.

Why it matters: A leaked token in a public log has to be rotated; deleting the log isn't enough.
Vocabulary check
Trigger
the event that starts a workflow.
Smoke test
a tiny, fast run that proves training still works at all.
Quality gate
the pass/fail comparison before a deploy.
Repository secret
an encrypted value a workflow can read but no one can print back.
Candidate
a model or agent version waiting to pass the gate.
Quick self-check before you continue
  • Why does a scheduled retrain go through the same gate as a code change?
  • Your gate checks MAE only. What could still ship that you don't want?
  • A workflow prints the token reversed. Why didn't masking hide it?
Check your thinking
  1. Because it's just another candidate. New data can make a model worse as easily as better, and the gate is what decides.
  2. Anything worse on a number the gate doesn't check: a slower model, a costlier one, or one that's worse for a single zone.
  3. Masking replaces the exact secret string. A reversed or encoded copy is a different string, so only a scan of the log output catches it.

3️⃣

Module 3: Observability, Evaluation & RAG Performance

HOS 3Outcome CO3 · CO4

Why before you start: A deployed model and agent get worse quietly. This module is about the signals that warn you first: what each one measures, how you know it's measuring the right thing, and what you'd do when it moves.

Data drift vs. concept drift

Data drift: the inputs change (new weather, a new zone, a stuck sensor). Concept drift: the relationship between inputs and outcome changes. A drift report compares each feature's current distribution with the training data and flags the ones that moved past a threshold.

Why it matters: Drift shows up before accuracy drops, because you don't know the true outcome yet.

Traces and spans

A trace is one request, end to end. Each step inside it (retrieval, a tool call, a model call) is a span with its inputs, outputs and duration. Langfuse stores them and lets you attach scores.

Why it matters: The slowest span is where latency comes from; the trace is where a wrong answer is explained.

Reasoning accuracy with an LLM judge

A second model grades each answer against a rubric. It scales, but it's a model too, so you check it: grade a sample yourself first, then compute agreement. Recheck when the judge's model changes.

Why it matters: A lenient or changed judge makes the agent look better than it is.

Latency: p50 and p95

The median (p50) is a typical request; p95 is the slow tail most complaints come from. Compute them per span name to see which step drives the tail.

Why it matters: An average hides the tail, which is what users notice.

RAG: speed and relevance

Context precision: how much of what was retrieved was relevant. Context recall: how much of what the answer needed was retrieved. Ragas scores both against known passages. Larger top-k usually raises recall, lowers precision and costs more prompt tokens.

Why it matters: CO4 asks you to optimise retrieval speed and context relevance, and that means trading them.

The vector database

Chroma and Qdrant store the same embeddings and return nearly the same passages. They differ in speed, filtering and how you run them. Relevance comes mostly from chunking and embeddings.

Why it matters: Benchmark before choosing, and don't expect the database to fix relevance.

An alert is a decision

Pick one signal, a threshold and a window, and justify the number from your own past weeks. Too loose hides drift; too tight wakes someone up every week.

Why it matters: Your Refine stage writes exactly one alert, with a test that it fires and one that it doesn't.
Vocabulary check
Span
one timed step inside a trace.
Judge
a model that scores another model's answer against a rubric.
Agreement
how often the judge's grade matches a human's on the same answers.
Top-k
how many chunks retrieval returns.
Context precision / recall
how much retrieved text was relevant / how much needed text was retrieved.
Quick self-check before you continue
  • Accuracy still looks fine but the drift report flags temperature. Why take it seriously?
  • The judge's average went up 0.1 this week and the human sample didn't. What changed?
  • Raising top-k from 3 to 10 raised recall. What did it cost?
Check your thinking
  1. Accuracy is measured only once true outcomes arrive. Drift in an input is an early warning that the model is meeting data it wasn't trained on.
  2. Probably the judge, not the agent. A model update or a looser rubric reading changes the scores. That's why the human sample is regular, not one-off.
  3. Lower precision (more irrelevant text in the prompt), more prompt tokens, and more latency in both retrieval and the model call.

Module 4: Security, Guardrails & Agent-to-Agent

HOS 4Outcome CO5

Why before you start: An agent that can act can be talked into acting wrongly. This module is about attacking your own agent first, layering defences that don't depend on the model behaving, and checking who's asking when another agent calls yours.

Prompt injection

Direct: the user tells the agent to ignore its rules. Indirect: the instruction hides in something the agent reads, such as a help article, an email or a web page. The model can't reliably tell data from instructions.

Why it matters: Every text the agent reads is a possible attacker, not just the user.

Excessive agency

The agent has more power than its task needs: a tool that can read any customer, a credit with no limit, an action no person approves. Most real damage comes from this, not from clever prompts.

Why it matters: OWASP lists it separately from injection for a reason.

Red-teaming

Attack your own agent with a suite of cases (promptfoo here), each repeated because attacks succeed only some of the time. Report rates per category, before and after guardrails.

Why it matters: Results that vary run to run are normal. Single outcomes aren't evidence.

Guardrails that hold

Four layers: least privilege (remove or scope the tool), marking input as data, an action check before each tool call (before_tool_callback in ADK) and an output check on each reply. The last two are code, so they hold even when the model is fooled.

Why it matters: No one layer stops everything. The suite shows which layer stops which attack.

A2A: agents calling agents

With the A2A protocol, one agent sends a task to another over HTTP, discovering what it can do from its agent card. The receiver checks who is calling and on whose behalf before any model call.

Why it matters: If the caller was itself injected, the receiver's checks are what still hold.

Frameworks for the report

The OWASP Top 10 for LLM Applications names the risk categories (prompt injection, sensitive information disclosure, excessive agency, system prompt leakage and more). The NIST AI RMF organises the work into Govern, Map, Measure and Manage.

Why it matters: Mapping findings to both is how an enterprise reads your red-team report.

Residual risk

Something always gets through: an attack that works sometimes, or a cost you chose to accept. Name it, and say who should know.

Why it matters: "Fully secured" is not a credible finding; a named residual risk is.
Vocabulary check
Indirect injection
an instruction hidden in content the agent reads, not in the user's message.
Least privilege
giving each tool and agent only the access its task needs.
Guardrail callback
code ADK runs before or after a model or tool call, which can block or change it.
Agent card
an A2A agent's description of itself: what it can do and how to reach it.
Residual risk
the risk left after your defences, named and accepted.
Quick self-check before you continue
  • Why is removing a tool stronger than an instruction not to use it?
  • All four layers are on and five $20 credits still go through. Which layer failed?
  • An unknown agent sends a task to your orders agent. What should happen first?
Check your thinking
  1. An instruction is followed by the model, which can be talked out of it. A tool that isn't there can't be called, however the request is phrased.
  2. None did: each credit is within the $25 limit. The rule checks one action, not the total, so it needs a per-order or per-day cap, or a person to approve it.
  3. The orders agent checks the caller against its allowlist and the customer scope, and rejects the task before any model call or data lookup.

Putting it together: all 4 HOS

Week 8 reviewTerm ProjectOutcome CO6

Why before you start: by Week 8 you've built every piece once. The Week 8 architecture review and your Term Project ask a different question: how the pieces connect, and which one catches which problem. Nothing here is new; it's the four modules, joined up.

The path of a change

A data batch or a prompt edit → versioned and validated (HOS 1) → CI's fast checks → the gate's evaluation against production → deploy, with the registry alias moved (HOS 2) → traces, judge scores, latency and drift watched (HOS 3). A retrain follows the same path.

The path of a request

A user's message → input marked as data → the agent reasons, retrieves and calls tools, each call checked before it runs → another agent called over A2A checks the caller → the reply passes the output check (HOS 4) → one trace, with a span per step and a judge score (HOS 3).

Quick self-check before the Week 8 review
  • Can you draw both paths above from memory, labelling each step with the HOS it came from?
  • Name one problem that no single layer catches on its own, and the two that catch it together.
  • Your agent's success rate went up 2 points after a prompt edit. What else do you need to know before you ship it?
Check your thinking
  1. If a step won't come to mind, reread that HOS's module above. Then step through the same paths in the Week 8 review.
  2. Drift: the drift report sees it, but only continuous training sends a fix through the gate. Or indirect injection: marking reduces it, and the action check stops what gets through.
  3. Whether 2 points is more than the run-to-run spread, what it did to cost per task and p95 latency, and whether the judge that scored it still agrees with human grades.
