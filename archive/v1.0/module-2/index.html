What's the HOS?

HOS 2 (Hands-On Skill) is this module's main build and 10% of your course grade. It has four stages across the two weeks: Create / Scaffold and Evaluate in Week 3, then Analyze and Understand & Refine in Week 4. All four go in one GitHub repo, and you submit that repo's link once, in Brightspace, at the end of Week 4. The Muddiest Point, Concept Debate, Application Challenge and Knowledge Check are graded separately.

HOS 1 made one run reproducible. HOS 2 makes every change go through the same steps automatically, so nobody deploys by hand from a laptop. CI runs the tests on every push, including data validation and a quick training smoke test. CD deploys what passed when a change is merged to main. CT, continuous training, retrains when it's time: on a schedule, or when the data has drifted.

Week 3 builds three GitHub Actions workflows around the HOS 1 pipeline and deploys the demand model and pantry_helper to a free Hugging Face Space, behind a quality gate: a candidate replaces what's deployed only if it's at least as good. For the agent, the gate is an evaluation run, and its scores vary. Week 4 is the harder half: explaining what the gate really compares, adding a condition to it by hand, and deciding which changes should trigger the full evaluation.

Anchoring analogy

A restaurant kitchen's pass. Every plate goes through the same window, where the head chef checks it against the order before it reaches a table, however busy the night is. CI is tasting as you cook, the quality gate is the pass, CD is the server who only carries plates that cleared it, and CT is re-checking the recipes when this week's produce isn't like last week's. A rollback is sending the old dish back out while the new one is fixed.

Learning objectives

By the end of the two weeks you will be able to:

  1. Explain what CI, CD and CT each add, and which events should trigger each one. CO2
  2. Automate tests, data validation and a training smoke test on every push with GitHub Actions. CO2
  3. Deploy a model and an agent on merge, only if a quality gate passes, and roll back in one step. CO2
  4. Design a quality gate for an agent whose evaluation scores vary from run to run. CO2
  5. Keep credentials in repository secrets, and prove they never reach the logs. CO2

Lecture: shipping every change the same safe way

≈ 60 min with videos3 short partsCO2

Three short segments instead of one long one: watch the video, read the notes, then try the quick check before moving on. The notes cover everything you need, so the videos are a second explanation rather than a requirement. If something stays fuzzy, that's exactly what your Muddiest Point is for.

Part 1 — CI, CD, and the third C ≈ 20 min

Watch first8:04 · GitHub

Watch for the three words you'll write in every workflow file: the event (on:), the job and its runner, and the steps. Everything in HOS 2 is those three, with ML steps inside. Open on YouTube (human captions).

CI: on every push, run the checks that are fast and cheap. For ML, that's unit tests, data validation and a smoke training run on a small sample, to prove the pipeline still runs, not that the model is good. CD: on merge, train for real, evaluate, and deploy what passed. CT: retrain when it's time, because a model goes stale even when nobody touches the code.

on: push              → tests, validate data, smoke-train, scan for secrets
on: push to main      → train, evaluate, [quality gate] → deploy to the Space
on: schedule (weekly) → drift check → retrain if needed → the same gate

Everything here is free: GitHub Actions minutes for your Classroom repo, and a free CPU Space on Hugging Face for the deployed demo.

⚠ Common mistakes

  • Full training in CI. CI should take minutes. Smoke-train on a sample; train for real only on merge.
  • Retraining on every push. A code change doesn't need new weights. CT is triggered by time or by drift, not by commits.
Quick check

Name one check that belongs on every push and one that only makes sense before a deploy. What makes the second one too slow or too expensive for every push?

Part 2 — Quality gates for models and agents ≈ 20 min

Watch first6:55 · IBM Technology

Watch for how evaluation replaces unit tests once a language model is part of the system. That evaluation is what your agent's gate runs. Open on YouTube (human captions).

A quality gate is a rule a candidate must pass before it replaces what's deployed: MAE no worse than the current model's, no worse on a key zone, latency under a limit. For an agent, the gate is an evaluation run on a fixed question set: success rate, cost per task and latency.

The agent's scores vary from run to run, so a gate that compares one run to one run will flip-flop. Two fixes, and you'll use both: run the evaluation more than once and compare averages, and leave a margin (a candidate must beat production by more than the run-to-run spread you measured in HOS 1, or at least not lose by more than it).

Worked example

A prompt tweak raises pantry_helper's success rate from 81% to 84%, and doubles cost per task because it now searches the help centre twice. A gate on success alone ships it. A gate on success and cost blocks it and says why. Neither gate notices the 3-point gain is inside the agent's normal spread of ±4 points, which is why the margin matters.

⚠ Common mistakes

  • A gate on one number. Gates only see what they measure.
  • A test set that changes. If the evaluation questions change between runs, the comparison means nothing. Version them (HOS 1).
  • No first-deploy rule. On the very first deploy there's nothing to compare against. Decide what the gate does then, and write it down.
Quick check

Your gate compares the candidate with the deployed model on a fixed test set. What happens to the gate's decisions if the test set itself is stale?

Part 3 — Secrets, rollbacks and continuous training ≈ 20 min

Watch first5:26 · IBM Technology

Watch for what happens after deployment: monitoring, retraining and eventually retiring a model. CT and rollback are how a pipeline handles those stages without a person doing them by hand. Open on YouTube (human captions).

Automated pipelines need credentials: a Hugging Face token to deploy, a Gemini key for the agent's evaluation. They go in repository secrets, which GitHub injects at run time and masks in the logs. Never in the code, never in a workflow file, never printed.

Every deploy needs a rollback: redeploy the previous registered version in one step. With the HOS 1 registry, that's moving the champion alias back and redeploying, not rebuilding anything.

CT is where MLOps and AgentOps differ most. The demand model retrains on new data. The agent rarely retrains at all, but its prompt, its tools and the model version underneath it change, and each of those changes should trigger the same evaluate-then-deploy gate.

⚠ Common mistakes

  • Trusting the mask. GitHub masks the exact secret string. A debug line that prints it base64-encoded, or one character at a time, gets through. Scan for it, and don't print it.
  • A rollback you've never tried. If the first time you roll back is during an incident, it's not a plan. HOS 2's Evaluate makes you do it once.
Quick check

Gemini quietly updates the model behind gemini-3.8-flash. Nothing in your repo changed. Which of your three workflows would notice, and when?

▶ Rehearse before the build: Open the CI/CD/CT Pipeline Simulator. Push the bigger, slower model with only the accuracy check on, then turn on the latency check and push it again.

New words this week (6)
CI / CD / CT
Continuous integration (test every change), deployment (ship what passes), training (retrain when it's time).
Workflow
A GitHub Actions YAML file: the events that start it, and the jobs and steps it runs.
Smoke test
A quick run on a small sample that proves the pipeline still works end to end, not that the result is good.
Quality gate
A rule a candidate must pass before it replaces what's deployed.
Repository secret
A credential stored by GitHub and injected at run time, never committed or printed.
Rollback
Redeploying the previous known-good version in one step.

    Concept Debate

    Discussion board · 3 stages
    This week's question

    Should a model or agent deploy automatically when it passes the gate, or should a person approve every production deploy?

    You'll argue a side you're assigned, then argue the other one, then drop advocacy and synthesize. Nobody gets to post "I agree" — by Stage 3 everyone has argued both sides.

    How your side is assigned

    Before the first debate you join Debate Group 1 or Debate Group 2, either assigned by your instructor or chosen yourself, as long as the two groups stay close to even. You stay in that group all term; find yours under Communication → Groups. The sides rotate each HOS, so nobody argues the same kind of position all term:

    HOS 1HOS 2HOS 3HOS 4Integration (Wk 8)
    Group 1Side ASide BSide ASide BSide A
    Group 2Side BSide ASide BSide ASide B

    Not in a group? (for example, you added the course late) Before posting Stage 1, count the posts on each side and join the side with fewer; if they're tied, take Side A.

    Side A — Deploy automaticallyGroup 2 this HOS

    If the gate passes, ship it.

    • People rubber-stamp approvals they don't have time to check.
    • Automatic deploys are small and frequent, so each one is less risky.
    • The gate holds the judgment: improve the gate, not the approval step.

    Side B — A person approves productionGroup 1 this HOS

    The gate recommends; a named person decides.

    • Gates only check what someone thought to measure.
    • An agent acts in the world, so a bad deploy has real consequences.
    • Accountability needs a name.
    AI use

    You may use an AI assistant to test your thinking, for example by asking it for the best objection to your side. Your posts must be your own words and your own reasoning: don't paste or lightly edit AI text. If AI changed your thinking, say how in one line. AI Use Guide →
