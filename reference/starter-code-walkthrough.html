How to use this page

Course rules this page follows: everything below runs in GitHub Codespaces and needs no credit card. Gemini, Hugging Face Spaces and Langfuse have free tiers; DVC, MLflow, pandera, Evidently, Chroma, Qdrant, Ragas and promptfoo run in your Codespace with no account.

What "starter code" means in this course

Each HOS has a starter template repository on GitHub, and you get your own copy by accepting that HOS's invite, linked from its lesson. The templates (AI430-HOS01 to AI430-HOS04) are planned: this page describes what each will contain. The same fictional business, Salish Fresh, runs through all four, but each HOS starts from its own repo, so you don't carry one HOS's bugs into the next. Your first job in each HOS is reading working code you didn't type.

Don't read ahead. HOS 2's starter contains a finished HOS 1 pipeline, and HOS 4's contains finished monitoring. Read a section only when you're starting that HOS.

1️⃣

Starting HOS 1

A working model and agent, no pipeline yet

The forecasting code, the data and the support agent all work. What's missing is everything that makes them reproducible: data versioning, validation, tracked runs and the registry. That's yours to build.

requirements.txt + .devcontainer/ — setup, done for you in a Codespace

GitHub builds a Python container, copies .env.example to .env and installs requirements.txt: dvc, pandera, mlflow, scikit-learn, pandas, google-adk and pytest. If a command says "not found", the Codespace was built before the config changed: Codespaces: Rebuild Container.

.env.example — where your key and the tracking server go 
# Your free Gemini API key — https://aistudio.google.com/apikey
GOOGLE_API_KEY=paste-your-key-here
GOOGLE_GENAI_USE_VERTEXAI=FALSE
MLFLOW_TRACKING_URI=http://127.0.0.1:5000

A template, safe to commit. Your real key goes in .env, which is git-ignored. MLFLOW_TRACKING_URI must match the server you start with mlflow ui --port 5000, or runs go to a local mlruns/ folder the UI isn't reading.

data/orders.csv — 52 weeks of orders for six zones

Columns date, zone, orders, temp_c, is_holiday. It isn't under DVC yet: the first commands in the HOS 1 guide put it there and commit the .dvc file instead.

data/batches/ — weekly batches, some broken on purpose

New weeks arrive here. A few are broken the way real data breaks, such as week-07-renamed.csv, where temp_c became temperature. Evaluate uses them to check your validation.

forecast/model.py — features and the model

Builds lag features, temperature and holiday flags, and trains a random forest with a fixed random_state. Reads the CSV with parse_dates=["date"]. Your pipeline calls it; you shouldn't need to change it.

pantry_helper/ — the support agent

A Google ADK agent on gemini-3.8-flash with tools search_help (the help centre), get_order and issue_credit (limit $25). In HOS 1 you don't change it; you evaluate it.

Watch out: If your assistant changes the model name to something like gemini-2.5-flash, new keys get a 502 or "model not found". Keep gemini-3.8-flash.
evals/questions.json + evals/run_agent_eval.py — the agent's evaluation

Ten customer questions with what a good answer must contain. python -m evals.run_agent_eval --runs 3 asks all ten three times and logs each run to MLflow with the prompt version and model name.

pipelines/ and dvc.yaml — yours (Create)

Empty except for TODOs. Your prompt has the assistant write pipelines/schema.py (the pandera schema), the train and evaluate scripts, and dvc.yaml with the stages validate → train → evaluate. In Refine you add one rule to schema.py by hand, with a test in tests/test_schema.py.

NOTES.md + screenshots/ — where your written work goes

One heading per stage. Your prompt, your Evaluate note, your Analyze walkthrough and your Understand explanation go here; screenshots go in screenshots/.

Before you prompt your assistant: run python -c "from forecast.model import train; print(train('data/orders.csv'))" once and read forecast/model.py, so you know what MAE to expect.

Repo: AI430-HOS01 (planned). Guide: HOS 1 guide.

2️⃣

Starting HOS 2

HOS 1's pipeline, plus a Space to deploy to

Your HOS 1 pipeline arrives finished, with an app for the Hugging Face Space, a gate script and a drift check. The three workflows that tie them together are yours.

requirements.txt + .devcontainer/ — setup, done for you in a Codespace

GitHub builds a Python container, copies .env.example to .env and installs requirements.txt: everything from HOS 1, plus gradio, huggingface_hub, evidently and pyyaml. If a command says "not found", the Codespace was built before the config changed: Codespaces: Rebuild Container.

app/ — what runs on the Space

app/app.py is a Gradio app with a forecast form and a chat box for pantry_helper. It loads the model behind the champion alias. app/requirements.txt is separate from the repo's own: the Space installs only that file.

Watch out: A Space that shows "Build error" is usually missing a package in app/requirements.txt.
gates/check.py + gates/thresholds.yaml — the quality gate

Loads the candidate's metrics and production's, compares them with the margins in thresholds.yaml, and exits non-zero with a message naming the check that failed. With no champion yet, it passes and registers the candidate. In Refine you add one condition by hand, with a test in tests/test_gate.py.

monitoring/drift_check.py — the trigger for retraining

Compares the latest batch with the training data and prints which features drifted. ct.yml runs it on a schedule and retrains only if it finds drift.

scripts/scan_logs.py — the secret scanner

Searches a job's output for strings that look like tokens, including reversed or encoded ones. GitHub's masking catches only the exact secret.

.github/workflows/ — yours (Create)

Empty. Your prompt has the assistant write ci.yml (tests, schema check, smoke test, secret scan on every push and pull request), deploy.yml (train, evaluate, gate, deploy on merge to main) and ct.yml (weekly drift check and retrain).

Watch out: Secrets aren't passed to workflows started by pull requests from forks, and a misspelt secret name gives an empty string, not an error.
Branches candidates/bigger-model and candidates/double-search — changes to sneak past your gate

Two ready-made candidates for Evaluate: a more accurate but slower model, and a prompt that doubles the agent's tool calls.

Before you prompt your assistant: add HF_TOKEN, GOOGLE_API_KEY and the HF_SPACE variable to the repo first (see Hugging Face setup), or deploy.yml fails on its first run.

Repo: AI430-HOS02 (planned). Guide: HOS 2 guide.

3️⃣

Starting HOS 3

An agent and a model to watch, and the data to watch them with

pantry_helper arrives with its help-centre index already built in both vector databases, a recorded week of questions and a judge rubric. Tracing, the judge, the drift report and the benchmark are yours.

requirements.txt + .devcontainer/ — setup, done for you in a Codespace

GitHub builds a Python container, copies .env.example to .env and installs requirements.txt: langfuse, evidently, ragas, chromadb, qdrant-client and google-adk; Docker is available for Qdrant. If a command says "not found", the Codespace was built before the config changed: Codespaces: Rebuild Container.

docker-compose.yml + rag/build_index.py — the two vector databases

docker compose up -d qdrant starts Qdrant; Chroma runs in-process. rag/build_index.py chunks the help articles and loads the same embeddings into both, so a comparison is fair.

observability/tracing.py — where tracing is set up

A stub that your Create prompt fills in: it connects to Langfuse with the three keys in .env and wraps each agent run in a trace, with a span per retrieval, tool call and model call.

Watch out: If every span has the same duration, the spans are created after the work instead of around it.
evals/week.json, evals/rubric.md + evals/run_week.py — a recorded week, and how to grade it

40 real-looking customer questions and a 1–5 rubric. python -m evals.run_week --questions evals/week.json --pause 4 runs them all and writes results/week.csv with each answer, its span timings and its judge score. evals/judge.py, the judge itself, comes from your prompt.

bench/questions.json + bench/ragas_setup.py — the retrieval benchmark's inputs

30 questions with the passages a good answer needs. ragas_setup.py points Ragas at Gemini instead of its OpenAI default; import it before running any metric. bench/retrieval.py is yours.

data/batches/week-09-sensor.csv + results/degraded-week.csv — known-bad cases

A batch with one feature shifted on purpose, for checking the drift report, and a week where quality drops, for checking the alert you write by hand in monitoring/alerts.py (Refine).

Before you prompt your assistant: start Qdrant and run python -m rag.build_index once, then ask pantry_helper two questions in adk web --allow_origins "*" so you've seen what a normal answer looks like.

Repo: AI430-HOS03 (planned). Guide: HOS 3 guide.

4️⃣

Starting HOS 4

An agent with every guardrail off, and an attack suite

pantry_helper arrives with its guardrails switched off, a separate orders_agent served over A2A, and a promptfoo suite of attacks. The guardrail callbacks are yours.

requirements.txt + .devcontainer/ — setup, done for you in a Codespace

GitHub builds a Python container, copies .env.example to .env and installs requirements.txt: google-adk with A2A support, and Node for npx promptfoo@latest. If a command says "not found", the Codespace was built before the config changed: Codespaces: Rebuild Container.

pantry_helper/serve.py + guards.yaml — the agent under attack

Serves pantry_helper on port 8000 for promptfoo. guards.yaml has four flags, all off: least privilege, input marking, action check and output check. pantry_helper/guards.py, which implements them as ADK callbacks, comes from your prompt.

a2a_orders/ — a second agent, over A2A

python -m a2a_orders.serve runs orders_agent on port 8001. It publishes an agent card, and checks each task's caller against an allowlist (AGENT_ID in .env) and the customer it's for, before any model call.

redteam/ — the attack suite

promptfooconfig.yaml has direct and indirect injection, excessive agency, disclosure and prompt-leakage cases, each repeated three times. poisoned_article.md is a help article with a hidden instruction. still_open.yaml has two attacks that four layers don't stop, for Refine.

Watch out: If your assistant edits a file in redteam/ to make a test pass, revert it with git checkout redteam/. The suite is the judge.
scripts/a2a_probe.py — an unknown caller

Sends a task to orders_agent as any agent id you give it. --agent-id stranger should be rejected before any model call.

pantry_helper/my_guard.py + redteam/my_cases.yaml — yours (Refine)

Empty. By hand, you write one callback that stops an attack still getting through, and add an attack case and a legitimate case for it.

Before you prompt your assistant: run the suite once with every flag off and screenshot the report. That's the baseline every later number is compared with.

Repo: AI430-HOS04 (planned). Guide: HOS 4 guide.

▶️

Running it

In a Codespace: on your repo, Code → Codespaces → Create codespace on main. The devcontainer installs everything and creates .env; add your keys to it. Then, from the repo's top folder:

# HOS 1 (mlflow ui in its own terminal tab)
mlflow ui --port 5000
dvc repro
python -m evals.run_agent_eval --runs 3

# HOS 2: push a branch and open a pull request; the workflows run in the Actions tab
git push -u origin my-change

# HOS 3
docker compose up -d qdrant
python -m evals.run_week --questions evals/week.json --pause 4
python -m bench.retrieval

# HOS 4 (three terminal tabs)
python -m a2a_orders.serve
python -m pantry_helper.serve
npx promptfoo@latest eval -c redteam/promptfooconfig.yaml

# Any HOS: the ADK developer UI
adk web --allow_origins "*"

Plain adk web shows a blank page in a Codespace, because ADK rejects requests through the forwarded URL; the --allow_origins "*" form is safe there, since Codespace ports are private to your account. Stop your Codespace when you're done: free hours are limited. More on the terminal, tabs and keys: Tools you'll use all term.

🔎

How to read code you didn't write

  1. Start at the entry point. That's dvc.yaml, a workflow file, evals/run_week.py or pantry_helper/serve.py, depending on the HOS.
  2. Follow one change or one request end to end. One batch through the pipeline, or one question through the agent, file by file, before you read anything else.
  3. Run it before you change it. Push a good batch, then a broken one; ask a question it can answer, then one it can't.
  4. Break it on purpose. Blank a key, rename a column, misspell a secret. Knowing how it fails is how you know you understand it.

This is the same habit the Evaluate and Analyze stages of every HOS are training.
