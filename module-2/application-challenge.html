Application Challenge 2: Harborview Mutual Claims-Intake CI

Take the CI/CD/CT pipeline from HOS 2 to a business you haven't seen: write the workflow for an insurance agency's claims-intake agent, set the threshold that blocks a release when the agent's scores vary, and decide which kinds of change must trigger the full evaluation.

Ground rules

Everything here runs in GitHub Codespaces on free tiers, with no credit card. The provided tests replay recorded agent runs, so they need no API key. The workflow runs in GitHub Actions on your repo's free minutes; there's nothing to deploy to, so the deploy step writes a release record instead.
🏢

The scenario

Harborview Mutual (fictional) is a regional insurance agency in Everett. Its claims-intake agent reads a customer's first message about a claim ("someone backed into my car in the Fred Meyer lot"), asks for what's missing, and files a structured claim for an adjuster. Changes have been deployed by hand, and last month a prompt edit made the agent stop asking for the policy number. Nobody noticed for nine days.

Two things you should know before you start:

  • The evaluation set is 25 recorded claim conversations (evals/claims/) with the fields an adjuster needs. A run scores the share of claims filed complete and correct.
  • Scores vary. evals/history.csv has the last 20 evaluation runs of the current production agent, with nothing changed between them: they range from 0.76 to 0.88.
📐

The spec

Every requirement below is checked by a provided test in tests/test_workflow.py.

PartMust doMust not do
.github/workflows/ci.ymlOn every push and pull request: run the unit tests and the claim-schema check.Run the full evaluation on every push.
.github/workflows/release.ymlOn push to main: run the evaluation, call gate.py, and write releases/<sha>.json only if it passes.Release when the gate fails, or skip the gate.
.github/workflows/watch.ymlOn a weekly schedule: evaluate production; if quality dropped below your threshold, open an issue and mark the previous release as the rollback target.Roll back silently, with no record.
gate.pyRead the threshold and margin from gate.yaml; exit non-zero with a message saying which number failed.Hard-code the numbers.
SecretsRead GOOGLE_API_KEY only from secrets; never print it.Put any key in a workflow file.

The open decision: the threshold that blocks a release

The claims manager's instruction: "I'd rather wait a week for a change than have another nine days of incomplete claims." Production scores between 0.76 and 0.88 with nothing changed. Set the gate: a fixed floor? Must a candidate beat production's average, and by how much? How many evaluation runs does a candidate get? Too strict and every release is blocked by noise; too loose and the policy-number bug ships again.

There's no single right answer, and no provided test for this case. You decide, implement it, prove it with your own tests, and defend it in DECISIONS.md.

🗂️

Which changes trigger the full evaluation

The full evaluation costs about four minutes and 300 model calls. The team wants to know when it's needed. You don't build these; in your memo, decide for each change: the full evaluation, the fast CI checks only, or something else, and say why.

  1. Fixing a typo in the agent's greeting.
  2. Rewording the instruction about which fields to collect.
  3. Adding a tool that looks up a policy by number.
  4. Upgrading to a newer version of the model.
  5. Changing the adjusters' claim form to add one optional field.
🪜

Steps & what to submit

1Open it and run the tests

Open your own AC 2 repo (Planned the AC 2 invite (the Classroom50 link is added here once the AI430-AC02 template repo is built and tested)) in GitHub Codespaces. Run pytest. The workflow tests fail until the files exist; the gate tests fail with NotImplementedError.

2Write the workflows and the gate

Write the three workflows and fill in gate.py until pytest passes. You may use an AI assistant; tell it to work in this existing workspace and not to edit the tests. The tests check your YAML's triggers and steps, and replay recorded runs through your gate.

3Set your threshold

Put your numbers in gate.yaml. Write at least two tests in tests/test_my_rules.py: one candidate your gate must pass and one it must block, taken from evals/candidates/, which includes the policy-number bug.

4Run it for real

Add GOOGLE_API_KEY as a repository secret, push a branch with the policy-number bug, and merge one with a harmless change. Link both workflow runs in RUNS.md.

5Write the memo

Fill in DECISIONS.md, about one page: your threshold and why, your call on each of the five changes, and what your AI assistant wrote, got wrong, or missed.

Submit (via Brightspace)
  • .github/workflows/, gate.py, gate.yaml and tests/test_my_rules.py
  • The output of pytest, pasted as text (all tests passing, including yours)
  • RUNS.md
  • DECISIONS.md

How it's graded

Each criterion is graded on one part of your submission, at one of three levels.

How this differs from HOS 2's Understand & Refine: there you extended code you already understood, by hand, with no AI. Here the business, the code, and the decisions are new, AI help is allowed (say what it wrote in DECISIONS.md), and half the grade (Analysis and Evaluation) is for the calls you make, not the typing.

🧯

Common snags

  • test_ci_runs_on_pull_request fails. on: needs both push and pull_request.
  • test_gate_reads_yaml fails. The threshold is hard-coded in gate.py. Read it from gate.yaml.
  • The release workflow can't see the key. The secret's name must match exactly, and secrets aren't available to pull requests from forks.
  • The scheduled workflow never runs. Schedules run only on the default branch. Use workflow_dispatch to test it by hand.
