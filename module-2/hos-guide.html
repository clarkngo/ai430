AIC 2: CI/CD/CT for Models & Agents

Write the three GitHub Actions workflows that ship Salish Fresh's model and agent: tests on every push, an evaluation gate before every deploy to a free Hugging Face Space, and a weekly job that retrains when the data drifts. Then try to sneak changes past them.

Before you start

  1. Check your account setup. This AIC needs a free Hugging Face account and write token, plus the GitHub account and Gemini key from AIC 1. Set them up first; the build won't run without them.
  2. Know the concepts. Read Concept Companion → Module 2 before you open the starter code.

What you'll need

  • Starter code: your AIC 2 repo, created from the AI430-AIC02 template when you accept the AIC 2 invite (Planned planned (the Classroom50 link is added here once the AI430-AIC02 template repo is built and tested)). Open it in GitHub Codespaces; dependencies install automatically. Not sure what a file does? See the starter code walkthrough for this AIC.
  • A free Hugging Face account, an empty Gradio Space on the free CPU hardware, and a write access token.
  • Two repository secrets, HF_TOKEN and GOOGLE_API_KEY, and one repository variable, HF_SPACE (for example your-name/salish-fresh), under Settings → Secrets and variables → Actions.
  • An AI coding assistant in your Codespace (Copilot Chat in Agent mode, or equivalent)

Reference reading (optional, before you start)

  • GitHub Actions quickstart, and using secrets.
  • Hugging Face Spaces overview.

This guide covers the build: Part A (Create / Scaffold, Evaluate) and the first half of Part B (Analyze, Understand & Refine). It is graded across those stages instead of on code correctness alone, for 60 of the 100 AIC points: 12 points each for Create, Evaluate, Analyze, Apply (the change you make by hand in Understand & Refine) and Understand (your own explanation of it, plus the short Post Mortem you write after the challenge). The other 40 points are the Part B challenge, in the challenge/ folder of the same repo. The whole AIC is graded once, at the end of Week 4. Each stage below says exactly what to submit. Everything goes in your Module 2 GitHub Classroom repo: written work under the matching heading in NOTES.md, screenshots in screenshots/. Commit and push as you go. By the end of Week 4, push your final work: your repo is your submission, so there is nothing to submit in Brightspace, and your last push before the deadline is what counts.

1 · Create / Scaffold

Graded under Build: Create, 12 of the 100 AIC points. The AI-assisted starting point, not the deliverable.

The starter is AIC 1's finished pipeline plus a Gradio app for the Space (app/: a forecast form and a chat box for pantry_helper), a gate script with its thresholds (gates/check.py, gates/thresholds.yaml), a drift check (monitoring/drift_check.py) and a secret scanner (scripts/scan_logs.py). Set up the Space and the secrets first (see Before you start), then prompt your AI assistant. Start from this prompt:

In THIS existing workspace (the starter-code folder that's already open),
edit files here; do not create a new workspace or project.
Write three GitHub Actions workflows in .github/workflows/:
- ci.yml on push and pull_request: install requirements, run pytest,
  run pipelines/validate.py on data/orders.csv, run
  pipelines/train.py --smoke (200 rows), and run
  scripts/scan_logs.py so the job fails if a secret appears in output.
- deploy.yml on push to main: dvc repro, then python -m gates.check
  (compares the new model and agent with production, using
  gates/thresholds.yaml); deploy app/ to the Hugging Face Space in
  HF_SPACE with huggingface_hub only if the gate exits 0.
- ct.yml on a weekly schedule and workflow_dispatch: run
  monitoring/drift_check.py; if it reports drift, retrain and run the
  same gate and deploy steps as deploy.yml.
Secrets come only from ${{ secrets.HF_TOKEN }} and
${{ secrets.GOOGLE_API_KEY }}; never echo them. Leave the numbers in
gates/thresholds.yaml as they are. MODEL stays "gemini-3.8-flash".

Push a branch and open a pull request: ci.yml should run. Merge it: deploy.yml should run the gate and deploy. Start ct.yml by hand from the Actions tab (Run workflow) to test it without waiting a week.

Submit
  • The prompt you gave your AI assistant, a screenshot of a green deploy.yml run, and a screenshot of your live Space.
🔍

2 · Evaluate

The critical gate — is the AI-produced result actually correct?

Each test tries to sneak something past the pipeline. At minimum:

  • A breaking change. Push a commit that breaks a unit test. Does CI fail before anything deploys? Does the Space keep serving the old version?
  • Better but slower. Merge the starter's candidates/bigger-model branch: lower MAE, three times the prediction latency. Does the gate notice?
  • A prompt that costs more. Merge candidates/double-search: a prompt edit that raises the agent's success rate slightly and doubles its tool calls. What does the gate say, and is the gain bigger than the spread you measured in AIC 1?
  • A leaked secret. Add a step that prints HF_TOKEN reversed. Does scan_logs.py catch it? Then delete that run's logs and remove the step.
  • Roll back. Move the champion alias back one version and run deploy.yml. How long did it take, and what did a user of the Space see meanwhile?
Submit
  • The workflow runs that prove each test (red and green), and a short note: what the gate caught, what it let through, and how the rollback went, with timings.
🔬

3 · Analyze

Why does this work, mechanically?

Pick one of these and explain it in your own words:

  • The quality gate. Walk through gates/check.py for one candidate: what it loads, what it compares, the margin, and the exact line that decides pass or fail. What does it do on the very first deploy?
  • When to retrain. Explain what ct.yml does with and without drift, why a retrained model goes through the same gate as a code change, and what should trigger the agent's evaluation instead, since it never retrains.
  • Secrets in CI. Trace HF_TOKEN from the repository settings to the line that uses it. What does GitHub's log masking catch, and what does it miss?
Submit
  • A written walkthrough of the one you chose (250–400 words), quoting the lines, log lines or trace steps you're explaining.
✋

4 · Understand & Refine

The mastery check — by hand, no AI assistance for this stage.

By hand this time — no AI assistance for this stage.

The gate compares MAE and success rate. Add one condition by hand, in gates/check.py, for something it can't see yet:

  • p95 prediction latency, cost per task (tool calls or tokens per question), or MAE on one zone.
  • Its number in gates/thresholds.yaml, with a one-line comment saying why that number.
  • A test in tests/test_gate.py with a candidate that passes the old gate and fails yours.
  • Two workflow runs: the old gate passing that candidate, and yours blocking it with a message that says which condition failed.
Submit
  • Your condition, its threshold and its test (Apply).
  • Your own explanation under Understand & Refine in NOTES.md: why this condition, why that number, what the gate still can't see, with screenshots of both runs (Understand).
🧯

Common snags

  • The workflow never starts — a YAML error. The Actions tab shows "Invalid workflow file" with the line. Indentation is two spaces, never tabs.
  • The deploy step says the token is empty — secrets aren't passed to workflows started by pull requests from forks, and a typo in the secret's name gives an empty string, not an error. Check the name in Settings.
  • The Space shows "Build error" — open its Logs tab. Usually a package missing from app/requirements.txt, which is separate from the repo's own requirements.
  • The gate fails on the first deploy — there's no production model to compare against. The starter treats "no champion yet" as a pass that registers the candidate; if your assistant changed that, put it back and say so in your Evaluate note.
  • ct.yml never runs on its schedule — scheduled workflows run only on the default branch, and can be delayed at busy times. Use Run workflow to test it.
  • 502 Bad Gateway, a 404 or "model not found" from the agent — almost always the model name. AI assistants default to whatever model was current in their training data, such as gemini-2.5-flash, which new API keys can't use. Set it back to gemini-3.8-flash. If that ever stops working, check the current list at ai.google.dev/gemini-api/docs/models.
  • 429 RESOURCE_EXHAUSTED — you hit the free Gemini tier's per-minute limit. Wait a minute and rerun; the starter scripts' --pause option adds a gap between calls.

Most snags trace back to a concept. If one doesn't make sense, see Concept Companion → Module 2.
