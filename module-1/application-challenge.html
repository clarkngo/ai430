Application Challenge 1: Rain City Bikes Demand Forecast

Take the data pipeline from HOS 1 to a business you haven't seen: turn a bike-share company's un-rerunnable notebook into a tested pipeline, decide which of three logged models to promote, and explain which of the notebook's old results can't be reproduced.

📏

Ground rules

Everything here runs in GitHub Codespaces on free tiers, with no credit card. The provided tests run on small fixture files, so they need no API key and no network.
🏢

The scenario

Rain City Bikes (fictional) runs 180 bike-share stations in Seattle. Its rebalancing vans move bikes overnight based on a demand forecast that a former analyst built in one notebook, notebooks/forecast_v3.ipynb. Nobody can rerun it: it reads a file called trips_final_FINAL.csv that's been overwritten twice, and its results table cites three models nobody can find. You're taking it over.

Two things about the data you should know before you start:

  • Station records are messy. Some stations report negative docks after a sensor reset, some appear twice after a renaming, and the test-fleet station ZZ-TEST should never be in training data.
  • The clock is fixed: the data runs to Sunday, November 1, 2026. Use bikes.clock.today(), never date.today().
📐

The spec

Every requirement below is checked by a provided test in tests/test_pipeline.py.

PartMust doMust not do
pipelines/validate.pyReject a batch with a clear message naming the failing check: unknown or test stations, negative docks, duplicate station-hours.Drop bad rows silently and carry on.
dvc.yamlDefine validate → train → evaluate, with the raw trips file as a DVC-tracked dependency.Read any file the pipeline doesn't declare as a dependency.
pipelines/train.pyLog params, the data version, MAE, p95 prediction time and the training data's end date to MLflow for every run.Log a run without its data version.
pipelines/train.pyRegister each model under bikes-demand, without moving the champion alias.Promote automatically.
ReproducibilityProduce the same MAE when rerun on the same data version and seed.Use an unseeded random split.

The open decision: which model to promote

Three candidates are already logged in the provided MLflow store (mlruns-fixture/): A, the most accurate, but the slowest to predict and trained on data that ends in June; B, slightly less accurate, fast, trained to October; and C, the fastest, least accurate, and the only one validated with the new schema. The operations lead's only instruction: "The vans leave at 2 a.m. The forecast has to be ready, and it has to be right about this season." Which one gets the champion alias, and what would make you change your mind?

There's no single right answer, and no provided test for this case. You decide, implement it, prove it with your own tests, and defend it in DECISIONS.md.

🗂️

The notebook's past results

The notebook's last cell has a results table: three models, three MAE numbers, and a note that model 2 "went to production in March". You don't fix the notebook. In your memo, say for each of the three results whether you could reproduce it with what's in the repo, and if not, exactly what's missing (the data version, a seed, a package version, a parameter). "I can't, because…" with the specific reason is a strong answer.

🪜

Steps & what to submit

1Open it and run the tests

Open your own AC 1 repo (Planned the AC 1 invite (the Classroom50 link is added here once the AI430-AC01 template repo is built and tested)) in GitHub Codespaces. Then run pytest. Almost everything fails with NotImplementedError. That's your to-do list.

2Build the pipeline

Fill in pipelines/ and dvc.yaml until pytest passes. You may use an AI assistant. If you do, tell it to work in this existing workspace and to keep the provided tests unchanged. Read what it writes: you'll defend it.

3Add your own rules

Write at least two tests in tests/test_my_rules.py: one for a validation rule you added, and one for the edge you think is most likely to go wrong (a station renamed mid-week, say).

4Compare the candidates

Start mlflow ui --backend-store-uri mlruns-fixture and compare A, B and C with your own run. Copy the comparison into RUNS.md, with the columns that decided your call.

5Write the memo

Fill in DECISIONS.md, about one page: your promotion decision and why, your verdict on each of the notebook's three results, and what your AI assistant wrote, got wrong, or missed.

Submit (via Brightspace)
  • pipelines/, dvc.yaml and tests/test_my_rules.py
  • The output of pytest, pasted as text (all tests passing, including yours)
  • RUNS.md
  • DECISIONS.md

How this differs from HOS 1's Understand & Refine: there you extended code you already understood, by hand, with no AI. Here the business, the code, and the decisions are new, AI help is allowed (say what it wrote in DECISIONS.md), and half the grade (Analysis and Evaluation) is for the calls you make, not the typing.

🧯

Common snags

  • test_rejects_test_station fails. The schema allows any station id. Check against data/stations.csv, and reject ZZ-TEST explicitly.
  • test_same_mae_on_rerun fails. Something is unseeded: the train/test split or the model. Both take random_state.
  • MLflow shows the fixture runs but not yours. Your runs go to the tracking URI in .env; the fixture is a separate store. Compare them side by side in RUNS.md.
  • A date test fails by one day. Somewhere you used date.today(). Use bikes.clock.today().
