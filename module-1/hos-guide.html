HOS 1: Pipelines, DataOps & Experiment Tracking

Turn Salish Fresh's forecasting notebook into a pipeline that remembers what it did: data versioned with DVC, every batch checked by a pandera schema, every training run and every agent evaluation logged to MLflow. Then find out what "reproducible" means for a model, and for an agent.

Before you start

  1. Check your account setup. This HOS needs a GitHub account and a free Gemini API key. Set them up first; the build won't run without them.
  2. Know the concepts. Read Concept Companion → Module 1 before you open the starter code.

What you'll need

  • Starter code: your HOS 1 repo, created from the AI430-HOS01 template when you accept the HOS 1 invite (Planned planned (the Classroom50 link is added here once the AI430-HOS01 template repo is built and tested)). Open it in GitHub Codespaces; dependencies install automatically. Not sure what a file does? See the starter code walkthrough for this HOS.
  • Your free Gemini API key (no credit card) from aistudio.google.com/apikey. In the repo: cp .env.example .env, then paste it in as GOOGLE_API_KEY.
  • Two terminal tabs: one for mlflow ui --port 5000, one for everything else.
  • An AI coding assistant in your Codespace (Copilot Chat in Agent mode, or equivalent)

Reference reading (optional, before you start)

  • DVC: Get Started — data versioning and pipelines, the first two pages.
  • pandera: DataFrame schemas.
  • MLflow Tracking and the Model Registry (aliases).

This HOS is graded across four stages instead of on code correctness alone: Engagement (Create/Scaffold) is 20% of the HOS grade, and Skills is 80%: Evaluate, Analyze, Apply (the change you make by hand in Understand & Refine) and Understand (your own explanation of it), 20% each. Each stage below says exactly what to submit. Everything goes in your HOS 1 GitHub Classroom repo: written work under the matching heading in NOTES.md, screenshots in screenshots/. Commit and push as you go, then submit the repo link to the HOS 1 assignment in Brightspace by the end of Week 2.

1 · Create / Scaffold

Graded as Engagement: 20% of this HOS. The AI-assisted starting point, not the deliverable.

The starter has a working notebook's logic split into plain Python (forecast/model.py: features and a random-forest model), 52 weeks of orders for six delivery zones (data/orders.csv), a folder of weekly batches, some of them broken on purpose (data/batches/), and pantry_helper, the Google ADK support agent, with ten evaluation questions (evals/questions.json). First, put the data under DVC and see what Git now tracks:

dvc init
dvc remote add -d local /workspaces/dvc-store
dvc add data/orders.csv
git add data/orders.csv.dvc data/.gitignore .dvc/config
git commit -m "Track orders.csv with DVC"

Start MLflow in its own terminal tab (mlflow ui --port 5000, then open the forwarded port), and prompt your AI assistant to build the pipeline. Use this prompt as given:

In THIS existing workspace (the starter-code folder that's already open),
edit files here; do not create a new workspace or project.
Turn the forecast notebook's steps into a DVC pipeline:
- dvc.yaml with three stages: validate (pipelines/validate.py),
  train (pipelines/train.py) and evaluate (pipelines/evaluate.py),
  with data/orders.csv as a DVC-tracked dependency.
- pipelines/schema.py: a pandera DataFrameSchema for orders.csv
  (date, zone, orders, temp_c, is_holiday), strict=True. validate.py
  exits non-zero with the failing check if a batch doesn't match.
- train.py logs to MLflow (tracking URI from .env): params, the data
  version (the md5 from data/orders.csv.dvc), MAE on the test split,
  and the model, registered as "demand".
- Don't change the features or the model in forecast/model.py.
Then make evals/run_agent_eval.py log each run of the 10 questions in
evals/questions.json to MLflow: prompt version, MODEL, and the score.
MODEL stays "gemini-3.8-flash".

Then run the pipeline and three agent evaluation runs:

dvc repro
python -m evals.run_agent_eval --runs 3
Submit
  • The prompt you gave your AI assistant, and a screenshot of the MLflow runs table showing the training run and the three agent evaluation runs.
🔍

2 · Evaluate

The critical gate — is the AI-produced result actually correct?

A pipeline that runs isn't the same as one that remembers what it should. At minimum, work out:

  • Reproduce a run. Check out your first run's commit, run dvc checkout, then dvc repro -f. Same MAE? If not, find what wasn't pinned (a seed, a package version, the data).
  • Break the data. Copy data/batches/week-07-renamed.csv over data/orders.csv and run dvc repro. Does validation stop it before train runs, with a message someone could act on? Restore the good file afterwards (git checkout data/orders.csv.dvc && dvc checkout).
  • Trace a model back. From the registered demand model, find the exact data version and parameters, using only MLflow and Git.
  • Agent variance. Compare the three evaluation runs of pantry_helper. How far apart are the scores? Would one run have been enough to judge a prompt change?
Submit
  • Screenshots of the rejected batch's message and the two matching runs, and a short note: what the pipeline caught, what wasn't pinned, and how far apart the agent's scores were.
🔬

3 · Analyze

Why does this work, mechanically?

Pick one of these and explain it in your own words:

  • What makes a run reproducible. List everything that has to be pinned for a rerun to match, and point to where your pipeline pins each one. Explain what dvc repro compares to decide a stage can be skipped.
  • Where validation sits. Explain why validate runs before train in dvc.yaml, what one check in schema.py would catch in real life, and one bad batch the schema would let through.
  • The registry. Explain the difference between the newest run, a registered version and the champion alias, and walk through a rollback.
Submit
  • A written walkthrough of the one you chose (250–400 words), quoting the lines, log lines or trace steps you're explaining.
✋

4 · Understand & Refine

The mastery check — by hand, no AI assistance for this stage.

By hand this time — no AI assistance for this stage.

Write one validation rule yourself in pipelines/schema.py, for a real failure you can imagine at Salish Fresh:

  • A check beyond types: a relationship between columns, a rule per zone, or a limit relative to recent history (for example, orders more than 5× the zone's median is a data error, not a busy day). pandera's pa.Check takes a function; a wide check can go on the whole schema.
  • A small bad batch in data/batches/ that breaks only your rule, and the rejection message it produces.
  • A test in tests/test_schema.py: one batch your rule rejects, one it accepts.
  • A good batch that still passes and trains, with both runs visible in MLflow.
Submit
  • Your rule in schema.py and its test (Apply).
  • Your own explanation under Understand & Refine in NOTES.md: what the rule protects against, one thing it still misses, and screenshots of the rejection and the good run (Understand).
🧯

Common snags

  • dvc repro says "Stage didn't change, skipping" — that's DVC working: the stage's inputs have the same hash as last time. Use dvc repro -f to force it.
  • MLflow shows no runs — the tracking URI in .env must match the server you started (http://127.0.0.1:5000). Without it, MLflow writes to a local mlruns/ folder that the UI isn't reading.
  • git status shows data/orders.csv as changed — it should be ignored. dvc add writes data/.gitignore; commit that file.
  • pandera says the date column has the wrong type — read the CSV with parse_dates=["date"], as forecast/model.py does.
  • 502 Bad Gateway, a 404 or "model not found" from the agent — almost always the model name. AI assistants default to whatever model was current in their training data, such as gemini-2.5-flash, which new API keys can't use. Set it back to gemini-3.8-flash. If that ever stops working, check the current list at ai.google.dev/gemini-api/docs/models.
  • 429 RESOURCE_EXHAUSTED — you hit the free Gemini tier's per-minute limit. Wait a minute and rerun; the starter scripts' --pause option adds a gap between calls.
  • A command says "not found" though the devcontainer should install it — the Codespace was created before the config changed. Command Palette → Codespaces: Rebuild Container. Your files are untouched.

Most snags trace back to a concept. If one doesn't make sense, see Concept Companion → Module 1.
