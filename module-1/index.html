What's the AIC?

AIC 1 (AI Challenge) is this module's main build: 100 points, 10% of your course grade. It runs in two parts. Part A: Build (Week 1): Create / Scaffold and Evaluate. Part B: Apply (Week 2): Analyze and Understand & Refine, then the individual challenge, which applies the same skill to a new scenario, and a short Post Mortem to close it. Everything goes in one GitHub repo, with the challenge in its challenge/ folder. Your last push before the end of Week 2 is your submission, and it's graded once: 60 points for the build and 40 for the challenge. The weekly Concept Debates and Knowledge Checks are graded separately.

Each activity below is tagged with its AI rule, from AI: expected in Create / Scaffold to No AI in Understand & Refine and the Knowledge Check. The AI Use Guide explains each one.

Building a model or an agent is the first 10% of the job. The other 90% is operating it: knowing which data, code, prompt and model version produced a result, and being able to produce it again. This course operates two systems all term for Salish Fresh, a fictional grocery-delivery co-op in Tacoma: forecast, a scikit-learn model that predicts tomorrow's orders per delivery zone, and pantry_helper, a Google ADK customer-support agent that answers from the help centre, looks up orders and issues small credits.

Week 1 compares three kinds of pipeline (software, MLOps, AgentOps) and builds the first layer of the MLOps one: the training data versioned with DVC, every batch checked by a pandera schema before it trains anything, and every run logged to MLflow, including three runs of the agent's evaluation. Week 2 is the harder half: explaining exactly what makes a run reproducible, writing a validation rule by hand, and deciding what "reproducible" even means for an agent whose answers vary from run to run.

Anchoring analogy

A lab notebook. A chemist who writes down only the result ("it turned blue") can't repeat the experiment. One who records the reagents, their batch numbers, the temperature and each step can, and can find out which change broke it next time. Data versioning is the batch numbers, the validation schema is checking the reagents before you pour, experiment tracking is the notebook, and the model registry is the shelf of results you trust enough to use.

Learning objectives

By the end of the two weeks you will be able to:

  1. Compare a traditional software pipeline, an MLOps (model-centric) pipeline and an AgentOps (action-centric) pipeline: what each versions, tests, deploys and monitors. CO1
  2. Version a dataset so any model can be traced to the exact data it was trained on. CO1
  3. Validate data before training, and decide what a validation failure should stop. CO1
  4. Track experiments (parameters, metrics, data version, artifacts) and promote a model through a registry. CO1
  5. Explain what reproducibility means for an agent whose output varies run to run. CO1

Part 1 — Software vs. MLOps vs. AgentOps ≈ 20 min

Watch first6:55 · IBM Technology

Watch for the parts of the ML lifecycle that a software pipeline doesn't have: data preparation, training and monitoring a model after it ships. Then ask which of them an agent also needs. Open on YouTube (human captions).

Go deeper (optional): IBM Technology, Large Language Model Operations (LLMOps) Explained (6:55, human captions): the same lifecycle for systems built on a language model, where prompts and evaluation take the place of training.

A software pipeline ships code: if the tests pass, the same code does the same thing. MLOps ships code plus data plus a trained model, and any of the three can change the result. AgentOps adds prompts, tools, memory and the model version, and an agent's answer can change from one run to the next even when nothing else did.

SoftwareMLOps (model-centric)AgentOps (action-centric)
What changes behaviourCodeCode, data, trained weightsCode, prompts, tools, memory, the model version
What you versionCode in GitCode in Git; data and models alongside itAll of that, plus prompts and the evaluation set
What you testUnit testsData validation, then metrics on held-out dataAn evaluation set, scored over several runs
What "broken" looks likeA failing testQuietly worse accuracyA wrong action, a loop, a confident wrong answer
What you monitorErrors, latencyDrift, accuracyReasoning accuracy, cost per task, unsafe actions

⚠ Common mistakes

  • Treating a model like code. Git shows you the training script didn't change. It can't show you that this week's data did.
  • Treating an agent like a model. A model's metric on fixed data is repeatable. An agent's score on the same questions varies, so one run proves little.
Quick check

pantry_helper's answers got worse this week. List everything that could have changed. Which of those would a plain Git history show you?

Part 2 — DataOps: version it, validate it ≈ 20 min

Watch first5:02 · DVCorg

No code, just the idea: Git tracks small pointer files while the data itself lives in a separate store. Watch for what gets committed and what doesn't. Open on YouTube (human captions).

Go deeper (optional): DVCorg, Versioning Data with DVC (Hands-On Tutorial!) (13:04, auto-generated captions only): the commands you'll run in AIC 1.

Data versioning gives each dataset a version the way Git gives code one, so "model v7" can point to "data v3". DVC does this by committing a small .dvc pointer file (a hash of the data) to Git, and keeping the data itself in a DVC remote. In AIC 1 the remote is a folder in your Codespace; a real team would use cloud storage, and the commands are the same.

Data validation checks a batch against a schema before it trains anything: the columns, their types, allowed ranges and values, no unexpected nulls. pandera writes the schema as Python:

schema = pa.DataFrameSchema({
    "date":       pa.Column("datetime64[ns]"),
    "zone":       pa.Column(str, pa.Check.isin(ZONES)),
    "orders":     pa.Column(int, pa.Check.ge(0)),
    "temp_c":     pa.Column(float, pa.Check.in_range(-20, 45)),
    "is_holiday": pa.Column(bool),
}, strict=True)          # strict: an unexpected or renamed column fails
Worked example

Week 7's batch arrives with temp_c renamed to temperature. Without validation, the feature code fills the missing column with a default, training succeeds, and the model is quietly worse on hot days. With the schema, the batch is rejected before training, with a message naming the column. Nothing about the code changed, so no code test would have caught it.

⚠ Common mistakes

  • Committing the CSV to Git instead of tracking it with DVC. It works for one small file and fails for real data, and the history fills with copies.
  • Validating after training. By then the bad batch has already produced a model someone might promote.
Quick check

A batch fails validation. Should the pipeline stop, train without the bad rows, or alert someone and carry on? What does each choice risk?

Part 3 — Experiment tracking and the model registry ≈ 20 min

Watch first9:38 · IBM Technology

Watch for the two halves of MLflow you'll use: runs with their parameters and metrics, and the registry that decides which model version is in use. The video also traces agents, which comes back in AIC 3. Open on YouTube (human captions).

Every training run records its parameters, metrics, data version and the model file it produced. MLflow keeps them in one table you can sort and compare, running inside your Codespace (mlflow ui). The model registry is where a run gets promoted: you give a model version an alias such as champion, and the app loads "the champion", not "whatever's newest". Rolling back is moving the alias.

For an agent, the "experiment" is an evaluation run: the prompt version, the tools, the model name and the scores on a fixed question set. Run it three times and you'll see the scores move even though nothing changed. That spread is the first fact of AgentOps.

with mlflow.start_run(run_name="rf-depth-8"):
    mlflow.log_params({"max_depth": 8, "data_version": data_hash})
    model.fit(X_train, y_train)
    mlflow.log_metric("mae", mean_absolute_error(y_test, model.predict(X_test)))
    mlflow.sklearn.log_model(model, "model", registered_model_name="demand")

⚠ Common mistakes

  • Logging the metric but not the data version. Then two runs with the same parameters and different results have no explanation.
  • Deploying "the latest run". The latest run is just the most recent experiment. Production is a decision, and the registry records who made it.
  • Judging an agent change from one evaluation run. Run it at least three times and compare the spread, not one number.
Quick check

The production model's accuracy dropped. Which two columns of the MLflow runs table would you look at first, and why?

▶ Rehearse before the build: Open the Data & Experiment Pipeline Simulator. Push a renamed-column batch with validation off, then find which run the regression came from.

Concept Debate A

CD01 · Discussion board · 3 stagesAI: think, don't write
This week's question

Should an agent's prompts be versioned and tracked like model weights, or treated like ordinary configuration?

You'll argue a side you're assigned, then argue the other one, then drop advocacy and synthesize. Nobody gets to post "I agree" — by Stage 3 everyone has argued both sides.

Before the first debate you join Debate Group 1 or Debate Group 2, either assigned by your instructor or chosen yourself, as long as the two groups stay close to even. You stay in that group all term; find yours under Communication → Groups. Your side switches with every debate, two a module (Debate A and Debate B), so nobody argues the same kind of position all term:

Not in a group? (for example, you added the course late) Before posting Stage 1, count the posts on each side and join the side with fewer; if they're tied, take Side A.

Side A — Track prompts like modelsGroup 1 this debate

Every prompt change is an experiment: versioned, evaluated and promoted.

  • A one-word prompt change can shift behaviour more than retraining.
  • Without tracking, you can't tell which prompt produced a bad week.
  • Evaluation scores need a version to attach to.

Side B — Treat prompts as configurationGroup 2 this debate

Keep prompts in Git with the code; skip the experiment-tracking overhead.

  • Git already versions text files.
  • Heavy process slows down the fast iteration prompts need.
  • The model version, not the prompt, is usually what changes behaviour.

Concept Debate B

CD02 · Discussion board · 3 stagesAI: think, don't write
This week's question

When incoming data fails a validation check, should the pipeline stop, or set the bad rows aside and keep running?

Same three stages as Debate A, and the same Debate Groups. This time your group argues the other side from the one it took in Debate A.

Side A — Stop the pipelineGroup 2 this debate

  • Nothing downstream trains or evaluates on data nobody has looked at.
  • A hard stop gets a person to fix the cause, not just the symptom.
  • A run that quietly drops rows can shift results without anyone noticing.

Side B — Quarantine and keep runningGroup 1 this debate

  • One bad batch shouldn't block every good row behind it.
  • The quarantined rows are kept, counted and reviewable later.
  • Stopping on every glitch trains the team to ignore or switch off the check.

The same AI rule applies: AI can help you think, but the posts are your own words.

Start by looking for an agent worth operating: a task someone at work, in an internship or in a CityU office does with documents, lookups and small actions. A good first question, from this week's lecture: what would have to be versioned for you to reproduce one of its answers next month?

Example — a campus IT help agent

It answers from the IT knowledge base (retrieval), opens or updates tickets (tools), and remembers each user's device and past issues (memory). AIC 1 versions its knowledge base and tracks every prompt change as an evaluated experiment; AIC 2 runs that evaluation on every pull request and deploys only if quality holds; AIC 3 traces every answer with a judge score and measures retrieval; AIC 4 red-teams it and lets it ask a separate accounts agent, over A2A, before it resets anything.
